# BACKEND_CANON — правила следования канону проекта для бэкендера

Версия 1.0 · 20.11.2026. Дополняет 08_BACKEND_HANDOFF v1. Цель — бесконфликтная стыковка с фронтендом, который собирается параллельно по `agent_pack/`.

## 1. Источники правды
| Что | Документ | Кто меняет |
|---|---|---|
| API (пути, поля, коды ошибок) | agent_pack/03_API_CONTRACT.yaml | только по согласованию владельца |
| Поведение (команды, тревоги, правила) | 08_BACKEND_HANDOFF.md, 06_MECHANICS_SPEC | владелец |
| Пожелания к бэкенду | BACKEND_REQUESTS.md | владелец добавляет, бэкендер отвечает статусом |
Расхождение реализации с контрактом = дефект бэкенда, пока контракт не изменён.

## 2. Канон API
1. Все пути — `/webhook/*`, JSON, UTF-8. Время — ISO 8601 с поясом (`2026-11-20T09:15:04+03:00`).
2. Ошибки — `{ "error": { "code", "message" } }`, коды из контракта; бизнес-отказ — 422, нет токена — 401, нет сущности — 404.
3. Авторизация — Bearer-токен из `/auth/login`; общий header-auth n8n в браузер не передаётся (может стоять на внутреннем уровне).
4. Имена полей — snake_case, как в контракте; null вместо отсутствующего поля.
5. Списки — массив на верхнем уровне; пагинация `limit/offset` там, где указано.
6. `POST /commands` идемпотентен по `idempotency_key` (повтор → 200 с той же командой).
7. `/updates?since=` — отдаёт всё изменённое строго после since и `server_ts` для следующего запроса; не терять события на границе (≥ since при равенстве — дедуп на клиенте по id).
8. Новое поле можно добавлять (клиент игнорирует лишнее); удалять/переименовывать — только через BACKEND_REQUESTS и новую версию контракта.

## 3. Канон поведения (не обсуждается)
1. «Выполнено» (acked) — только по ack модема с совпавшим cmd_id; sent_gw ≠ выполнено.
2. Команда on без длительности получает default; > max → 422 DURATION_OVER_MAX (не урезать).
3. Команда off — без подтверждения всегда.
4. BACKLOG и неназначенные каналы не запускают тревоги и правила.
5. Пропущенные запуски расписаний не догоняются; причина — в журнал.
6. Журнал аудита — только INSERT; actor обязателен.
7. Каналы оповещения фильтруются `client_settings`; недоступный канал — запись в журнал, не ошибка.
8. Перепривязка канала не меняет историю.

## 4. Тег и время
- tag_id = `{dev_eui}/{param_code}/{level_cm}/{sensor_no}` (десятичные числа, без ведущих нулей: `70B3D58FF0031A01/3/-10/1`).
- ts_measured — время измерения (cycle_ts/записи), ts_received — ts_server.
- quality — одно из: good, stale, offline, out_of_range, sensor_error, sim.

## 5. Тестовый стенд и проверка
- Фронтенд-агент поставляет тест «ответ ↔ схема»; бэкендер прогоняет его против стенда перед каждой поставкой.
- Перед стыковкой — разделы B и C из agent_pack/09_INTEGRATION_CHECKLIST.
- Дефекты стыковки — issues с меткой `integration` и указанием стороны.

## 6. Безопасность (из брифинга бэкенда, без изменений)
UI n8n и bridge наружу не проксировать; секреты только в .env; Caddy: `/webhook/*`, `/dash/*`, остальное 403; пароли пользователей — хэш; rate-limit на /auth/login.

## 7. Открытые пункты к бэкенду (ответить статусом в BACKEND_REQUESTS)
BR-1 object_type (внесено в HANDOFF); BR-2 posts.scene_x/scene_y; формат подписанных каналов (прошивка); формат порта 3; механизм sent_gw в Vega Server; push в режиме per-клиент.
