# README_DEPLOY — сборка и выкладка прод-сборки Agro-SCADA Lite

Как собрать фронтенд без мока и выложить его в каталог Caddy. Пункты чек-листа интеграции: 09_INTEGRATION_CHECKLIST, часть A.

## Требования

- Node.js и npm. Проверено на Node v24.19.0 и npm 11.17.0.
- Каталог `app` репозитория фронтенда.

## Сборка

1. Установить зависимости точно по lockfile:

   ```bash
   npm ci
   ```

2. Собрать прод-версию:

   ```bash
   npm run build
   ```

   Команда запускает `tsc -b` (проверка типов) и `vite build` (сборка). Production-режим читает `VITE_USE_MOCK=false` из `.env.production` — мок MSW и панель отладки не попадают в бандл. Если в системе или в `.env.local` задан `VITE_USE_MOCK=true`, явно переопределить: `VITE_USE_MOCK=false npm run build`.

3. Результат — каталог `dist/`: `index.html`, ассеты с хэшами в имени, `manifest.webmanifest`, `sw.js`, иконки PWA.

## Проверка сборки

- Поиск по `dist/` не находит `mockServiceWorker.js`, строки «Мок» и панель отладки (чек-лист A1).
- Пути в `dist/index.html` начинаются с `/dash/` (`/dash/assets/...`) — базовый путь из `VITE_BASE_PATH`.
- В бандле нет абсолютных адресов API: все запросы уходят на `VITE_API_BASE` (`/webhook`). Единственный внешний абсолютный URL — `https://tile.openstreetmap.org/...`, тайлы карты Leaflet (по спеке 05 §3).

## Переменные окружения

| Переменная       | Значение   | Назначение                                                                             |
| ---------------- | ---------- | -------------------------------------------------------------------------------------- |
| `VITE_USE_MOCK`  | `false`    | исключает мок MSW и панель отладки из бандла                                           |
| `VITE_API_BASE`  | `/webhook` | базовый путь всех запросов к API; тот же домен, что и `/dash` — CORS не нужен          |
| `VITE_BASE_PATH` | `/dash/`   | префикс маршрутов и ассетов; манифест и service worker PWA учитывают его автоматически |

Значения по умолчанию живут в `.env.production` репозитория.

## Выкладка

1. В конфигурации Caddy: блок `/dash/*` ведёт на каталог со сборкой (`dist`) и содержит fallback на `index.html` для SPA-маршрутов; `/webhook/*` проксируется в n8n. Подробно — 09_INTEGRATION_CHECKLIST, часть C.
2. Скопировать содержимое `dist/` в каталог, на который смотрит блок `/dash/*`.
3. TLS должен быть включён: установка PWA и service worker работают только по HTTPS (09, C3).

## Проверка после выкладки

1. Открыть `https://<домен>/dash/` — открывается экран входа.
2. Обновить страницу на внутреннем маршруте (например `/dash/o/1`) — сервер возвращает приложение, а не 404 (SPA fallback).
3. В DevTools → Application: загружен `manifest.webmanifest`, service worker `/dash/sw.js` в состоянии activated.
4. Вход реальным пользователем: `/auth/login` отвечает Bearer-токеном. Для этого должна быть готова часть B чек-листа (бэкенд).

## Обновление и откат

- Хранить две последние сборки; откат — вернуть на место предыдущий `dist` (09, E4).
- Service worker обновляется автоматически (`registerType: autoUpdate`): после выкладки новой сборки клиент получает новую оболочку при следующей загрузке страницы.
