# 01_README_AGENT — инструкция для кодинг-агента

Версия 1.0 · 20.11.2026 · Агент: Zcode (GLM 5.3) · Репозиторий: GitHub (выдаёт владелец)

## 1. Задача
Собрать фронтенд «Agro-SCADA Lite» — адаптивное веб-приложение (PWA) для мониторинга агро-объектов и управления исполнительными устройствами через LoRaWAN-модемы. Бэкенд (n8n + PostgreSQL) делает другой исполнитель. Ты работаешь против мок-сервера по контракту и готовишь приложение к переключению на реальный API одной настройкой.

## 3. Рекомендованный стек (можно заменить с обоснованием в DECISIONS.md)
- React + TypeScript (strict), Vite; сборка — статика, base path `/dash/`.
- Данные: TanStack Query (кэш + периодический опрос). Состояние UI: Zustand.
- Графики: Apache ECharts (наложение рядов, 2 оси Y, зум). 3D: three.js через @react-three/fiber.
- Карта: MapLibre GL или Leaflet (интернет есть).
- PWA: vite-plugin-pwa (manifest, установка на экран; офлайн-режим не требуется, только кэш оболочки).
- Мок: MSW (Mock Service Worker) — работает в браузере, тот же контракт.
- Тесты: Vitest + Testing Library; e2e — Playwright (ключевые сценарии).
- Стиль: CSS-переменные из DESIGN_TOKENS; допустим Tailwind, если токены вынесены в конфиг.

## 4. Непреложные правила
1. API — только по 03_API_CONTRACT. Не придумывать эндпоинты и поля. Нужно новое → записать в `docs/CONTRACT_REQUESTS.md`, не реализовывать молча.
2. Все запросы — через один модуль `src/api/` с базовым URL из `VITE_API_BASE` (по умолчанию `/webhook`). Переключение мок ↔ реальный: `VITE_USE_MOCK=true|false`.
3. Токен: `Authorization: Bearer <token>` после `/auth/login`. Никаких ключей и паролей в коде и репозитории. 401 → на экран входа.
4. Честный статус: «Выполнено» показывать только при статусе команды `acked`/`completed`. `sent_gw` = «Передано шлюзом», не выполнено.
5. Любое значение на экране сопровождается качеством и временем (`ts_measured`, при отсутствии — `ts_received` с пометкой «время приёма»).
6. Команда `on` без длительности не отправляется — подставлять `default_duration_s`; превышение максимума — показывать ошибку, не урезать.
7. Все тексты интерфейса — на русском, вынесены в `src/i18n/ru.ts`.
8. Время отображать в поясе объекта (по умолчанию Europe/Moscow), формат «20.11.2026 09:15».
9. Не трогать бэкенд, n8n, Caddy, БД. Сборку класть в `dist/` для `/dash/*`.
10. Каждая задача из TASKS_PLAN — отдельная ветка и PR; в описании PR — номер задачи и выполненные критерии приёмки.

## 5. Порядок работы
1. Прочитать весь пакет. Вопросы и противоречия — в `docs/QUESTIONS.md`, затем продолжать по допущению, пометив его `[ASSUMPTION]`.
2. Выполнять задачи TASKS_PLAN строго по порядку; не начинать следующую, пока не пройдены критерии текущей.
3. После каждой задачи: `npm run lint && npm run test && npm run build` без ошибок.
4. Обновлять `docs/PROGRESS.md`: задача, статус, ссылка на PR, отклонения.

## 6. Определение готовности (DoD) всего фронтенда
- Все задачи TASKS_PLAN закрыты, критерии приёмки выполнены на моке.
- Lighthouse (мобильный): PWA устанавливается, Performance ≥ 80, Accessibility ≥ 90.
- Работает на ширине 360 px и 1920 px.
- Переключение на реальный API выполняется только переменными окружения (проверка по 09_INTEGRATION_CHECKLIST).

## 7. Чего не делать
- Не использовать готовые SCADA/IoT-платформы и их код (ThingsBoard, FUXA и т. п.).
- Не хранить секреты; не логировать токены.
- Не добавлять роли и права (в MVP одна роль).
- Не реализовывать бизнес-логику бэкенда на клиенте (правила, эскалацию, таймауты команд) — клиент только показывает статусы из API.
